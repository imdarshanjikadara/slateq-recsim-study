# Deviations from the approved proposal

Every change relative to `docs/proposal.md` is logged here with date, reason and impact.
The report's "Deviations" section is built from this file.

| # | Date | Deviation | Reason | Impact on the science |
|---|---|---|---|---|
| D1 | 2026-11-05 | **Modern software stack** (Python 3.14, numpy 2, PyTorch, gymnasium) instead of RecSim's original TF1 / dopamine / gym stack. | Instructed by the student: use current, lightweight library versions. RecSim's original stack does not import on current TensorFlow. | Environment unchanged (see D2). Learning agents are re-implemented (see D3). |
| D2 | 2026-11-05 | RecSim's environment is loaded from `third_party/recsim` (unmodified) through an **import shim** (`gym` → `gymnasium.spaces`, `gin.tf` → `gin`, TF-importing package `__init__` files bypassed). | Lets us keep RecSim's original Interest Evolution user model, reward, choice model and dynamics without TensorFlow. | None intended: the simulator code is RecSim's own. Verified in Phase 0 (`results/recon/env_probe.json`). |
| D3 | 2026-11-05 | **SlateQ is our own PyTorch port** of RecSim's `SlateDecompQAgent` (top-k selection, SARSA target, same network shape and scoring functions). The proposal says "SlateQ agent from RecSim". | RecSim's agent depends on TF1 + dopamine (excluded by D1). | We cannot run RecSim's TF agent side by side. Mitigation: unit tests against RecSim's NumPy `score_documents` and against the paper's equations (Phase 3). Hyperparameter defaults are taken from the reference where they are readable in source; the rest are documented as our choices. |
| D4 | 2026-11-05 | Naming correction: the proposal's "Full SlateQ Agent" means the **decomposed** SlateQ (`SlateDecompQAgent`). RecSim's `FullSlateQAgent` is the non-decomposed baseline. | Found while reading the RecSim source. | Wording only; the research questions are unchanged. |
| D5 | 2026-11-05 | "Catalog size" is operationalised as RecSim's `num_candidates` (N), the candidate set **redrawn every step** (`resample_documents=True`). | RecSim has no fixed catalogue in Interest Evolution: documents are sampled fresh each step. | Must be stated in the report. Confirmed by the student on 2026-11-05 (RECON Q1). |
| D6 | 2026-11-05 | The SlateQ port follows the **RecSim reference's null-item handling**: the no-click option enters choice probabilities, but its continuation value Q̄(s,⊥) is 0, and only clicked transitions are trained. The paper's decomposition (§3–4) includes ⊥ in the slate sum. | Faithful to the reference implementation the proposal names; decided by the student (RECON Q2). | Targets omit the value of continuing after a no-click. Stated as a limitation in the report. |
| D7 | 2026-11-06 | **Learned-myopic ablation** added: the SlateQ port with γ = 0 (RecSim's `myopic_slate_topk_sarsa`). | Isolates the effect of long-term reasoning: same network, optimiser, data, training budget and tuning budget. *Corrected 2026-11-13:* the horizon is not the only difference, because each agent uses its own tuned learning rate (PROTOCOL 12.6). Phase 6b E1 (D14) measures this. Pre-approved addition in the scope contract. | Extra baseline; the oracle-myopic baseline is kept unchanged. |
| D8 | 2026-11-06 | SlateQ port details that differ from, or cannot be checked against, the TF reference: ε decays over 100K steps (dopamine default 250K); ε_eval = 0 (reference 0.001); torch RMSProp puts eps outside the square root (TF inside); dopamine defaults for γ, replay, schedule are taken from dopamine's documentation, not verified against its source. Training episodes are cut at the exact step budget and the cut is treated as a truncation (bootstrapped). | Fit the 300K–500K budget; deterministic evaluation; equal budgets for all agents. | Small; all choices fixed in PROTOCOL §12 before any run, and identical for SlateQ and learned-myopic. |
| D9 | 2026-11-06 | **FullSlateQ not run** (proposed, declined). Only its action count (number of ordered slates N!/(N−k)!) is reported, as an intractability figure. | (a) With candidates redrawn every step (D5), a Q-value per slate *index* is attached to different documents at every step, so a non-decomposed Q over enumerated slates has no stable meaning in this environment; a fair version would need a different architecture, which is a new method (out of scope). (b) Time: it is the first optional item to cut under the project timeline. Decided with the student 2026-11-06. | None on RQ1–RQ3. The report states that decomposition is compared only through its action-count argument, not empirically. |
| D10 | 2026-11-06 | **RQ2 grid** N ∈ {5, 10, 20, 40, 80} × k ∈ {2, 3, 5} (k < N) plus the degenerate control (5, 5). The proposal names catalog and slate size but no values. | Chosen from measured throughput (`results/protocol/timing.json`), before any eval-stream run. | Defines RQ2's scope. |
| D12 | 2026-11-06 | RQ3's proportional-cascade condition uses a **numpy-2-compatible subclass** of RecSim's `ProportionalCascadeChoiceModel` (`src/slateq_study/choice_compat.py`). | RecSim's check `assert not scores[scores < 0.0]` raises on an empty array under numpy 2, so every cascade episode failed (found by the RQ3 pilot before any real RQ3 run). The subclass performs the same check as `not (scores < 0).any()` and reuses RecSim's maths (tested against it). | None on behaviour; the matched model and the RQ2 runs do not use this class. |
| D11 | 2026-11-06 | **RQ3 oracle under cascade models** ranks candidates with the proportional model on the true user features (not the cascade model itself). | Cascade scores in RecSim are position-dependent over the candidate list; ranking candidates with them would penalise later candidates for no reason. The proportional ranking equals the cascade's per-item click-propensity ranking (tested in `tests/test_rq3.py`). | Oracle remains the myopic click-maximiser in every RQ3 condition. |
| D13 | 2026-11-13 | **Phase 6b follow-up experiments E1–E5** (PROTOCOL §16), added after the Phase 6 results were seen: matched learning rates (E1), a planning-horizon curve over γ (E2), twice the training budget at (80, 3) (E3), the SlateQ paper's cascade (E4), and clicks versus watch time from existing runs (E5). | The literature review showed RQ1 repeats the SlateQ paper's own comparison, and the Phase 6 results left open questions: the learning-rate difference, the horizon, whether learned-myopic is under-trained at N = 80, and why our cascade result differs from the paper's. | Exploratory and labelled as such. No Phase 6 verdict, setting, seed or metric changes. Results go in a separate addendum. |
| D14 | 2026-11-13 | **Agent variants** in the sweep runner: a learned agent with only `learning_rate`, `gamma` or the budget (whole-number factor) changed. Baseline runs are **reused from rq2**, not rerun. | Needed for E1–E3 without retyping frozen values; reuse avoids spending ~10 CPU-hours re-running identical configurations. | None on earlier runs: their job keys and configs are unchanged (tested). Phase 6b runs come from a later commit; agent, env and harness code are unchanged, checked with `make demo`. |
| D15 | 2026-11-13 | **E4 cascade implemented by us** (`src/slateq_study/paper_cascade.py`) from the SlateQ paper's §6.3 description: β0 = 1.0, β = 0.65, conditional-model base probability, no-click option kept. The position index j is read as starting at 0. | RecSim has no such class: its cascades use a constant attention probability and a 0.05 score scaling. third_party/recsim stays read-only. | A different user model from our RQ3 severe rung. Results are context for the paper's §7.3, not a replication of its numbers (different implementation). |
| D16 | 2026-11-13 | **New metrics for E5:** click rate per step and watch time per click, computed from the per-episode logs already saved by every run. | To ask whether the click-maximising baseline gets more clicks but less watch time than SlateQ. | Analysis only. Simulator-only statement; nothing is claimed about any real platform. |
